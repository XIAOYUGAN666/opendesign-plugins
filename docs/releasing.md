# Independent candidates and approved Stable publication

## Plugin branding assets

Root `plugin.json` may declare presentation under `extensions.com.openai.interface`: display name, descriptions, developer/category/capabilities, HTTPS links, brand colors, and `logo`/`composerIcon` with optional dark variants. Screenshots and starter prompts are not implemented by OpenDesign. Referenced images belong under `./assets/`; retain official download provenance and SHA-256 in `assets/SOURCES.json`. Do not identify the software vendor as the plugin developer.

Both Provider staging adapters copy `assets/`. Common source closure, final artifact verification and Stable projection validate declared asset containment, presence, supported formats and limits. Images participate in the existing file inventory and signed portable view. Each icon must be square, 48–4096 pixels, and at most 1 MiB; portable market totals retain the Host's 8 MiB bound. Host decoding is independently bounded and converts SVG to PNG without external resources. Optional missing fields retain compatibility with older released packages.

The standard-library candidate verifier checks image containers and dimensions; it is not a full raster decoder. Before approving a candidate, also run the production Host's `plugin_presentation` integration test with `PLUGIN_ASSET_CANDIDATE_ROOT` pointing at that independently extracted candidate and `--include-ignored`. This separately proves the declared images actually decode through the same bounded implementation used by native IPC. Neither check proves a Tauri WebView installation or live engineering operation.

RFEM 0.1.2 and Rhino 0.1.16 provide plugin-owned branding assets. They are independently signed Releases, with coordinated discovery at marketplace sequence 2. Native Rhino bindings and release inputs must be regenerated after all byte-sensitive build inputs are finalized. Local source edits and candidate verification never change installed applications; the application consumes the signed market and updates through its plugin page.

## Verification and candidate workflows

Run root checks with `python -B -m unittest discover -s tests -v`. Cryptographic and runtime checks execute through the existing independent fixture tool environment, prepared from `tests/fixtures/fixture-engineering/provider/` with `uv sync --frozen --extra test --extra build`. Run its tests there with `uv run --frozen --extra test python -B -m pytest -q`.

Both workflows pin official action commits, Windows 2025, Python 3.12.10 and uv 0.9.21; projects consume their own frozen locks. `verify.yml` has root binding checks, independent fixture checks and two independently resolved Provider projects. An absent project is `notPresent`, not a Provider test/build pass. Once a real Provider migrates, its own checks run in its own job/environment.

The manual `release-plugin.yml` defaults to `operation=build`, validating/building the selected fixture, RFEM or Rhino project. It derives the version from the selected root, checks the project version, and independently verifies the unsigned archive. Real Provider binaries are not uploaded as public Actions artifacts. The default/build job has `contents: read` only. The separate manual signing job has the narrowly documented write-capable token needed to read draft releases; its reviewed steps do not create/publish Releases, tags or formal marketplace entries.

Actions artifacts in this public repository are public evidence, not private channels. Binary uploads are limited to safe synthetic fixture candidates. The explicit `sign-draft` operation may retain a public signed receipt, without the real ZIP, secrets or engineering data. The publisher separately prepares an authorized draft and checks actual bytes; no workflow operation publishes Stable. See the controlled signing boundary below.

## Controlled signing and coordinated identity migration

The only current signing IDs are `rfem-publisher-v1` and `rhino-publisher-v1`, using independent Ed25519 keys in the existing Environment. The publisher authorized a development-stage Breaking Refactor after normal Host uninstall/maintenance settlement of the old installations. The old RFEM ID, Rhino previous key, retained-key support, signing aliases/fallbacks and obsolete bundled catalog entries were removed. Current Host policy contains exactly the two new public keys. Old receipt fixtures exist only as rejection tests, never installation authority. The policy is exported byte-for-byte to `schemas/host-publisher-policy.json` through `scripts/import_contracts.py --publisher-policy`; its source and SHA256 are in the owner inventory. This public export is a signing-tool reference, not a new Host trust source. It contains no private key and must never be edited manually. The private application repository need not be exposed or made accessible to the plugin workflow.

In repository **Settings → Environments → plugin-signing → Environment secrets → Add environment secret**, enter `RFEM_PUBLISHER_V1_KEY_B64` and `RHINO_PUBLISHER_V1_KEY_B64`. Each value must be strict standard Base64 of the corresponding **32-byte raw Ed25519 private seed** matching the exported Host public key, not a PEM file, Dlubal API Key or GitHub token. Never send either value through chat. No keys are generated or rotated by these tools. Missing, malformed, swapped, shared or mismatching keys fail closed with a fixed error category and no signed output.

Dispatch `release-plugin.yml` from `main` with `operation=verify-keys` first. The signing job references the existing `plugin-signing` Environment and has its own main-only guard and serialized concurrency. GitHub only exposes draft releases to identities with push access: the real read-only-token run failed before secrets with `Exact draft was not found`. Therefore only this job uses `contents: write`; the workflow default and build job remain read-only. The token is explicitly passed only to release-list/download GET steps, checkout does not persist it, and the signing step/Provider does not receive it. This is write-capable token authority, not a technical impossibility of publication; reviewed workflow operations perform no Release/tag/Marketplace write. A future publication command still requires separate final approval. See [GitHub draft release visibility](https://docs.github.com/en/rest/releases/releases#list-releases). The checked Environment currently permits exactly the `main` branch; no reviewer rule is configured. Branch restrictions and key verification do not grant Stable approval. Secrets are injected only into the signing step, not checkout, dependency setup, downloads or build steps. `publisher_signing.py` immediately removes both secret variables from its process environment, strictly decodes them in memory, compares derived public keys to the owner export, and leaves them out of Provider child environments. It additionally rejects exact raw/Base64/hex private material found in tracked source before producing a signature. It emits only public fingerprints, current key IDs and safe error categories; private material never enters arguments, log output or files. The standalone `sign_envelope.py`/`sign_marketplace.py` interfaces continue to use raw anonymous stdin.

`operation=sign-draft` additionally requires a real package, its exact `plugin-<id>-v<root-version>` draft tag and independently reviewed lowercase archive SHA256. The draft must target the exact workflow commit; an already existing tag must resolve to that commit. Drafts are selected from the authenticated release list, not the published-release-by-tag endpoint. The GET-only download step verifies draft status, unique bounded ZIP/unsigned receipt assets and the supplied digest. The existing archive verifier then checks complete bytes, inventory and metadata-only MCP discovery. The signer creates a **new** receipt under the target ID, keeping ZIP/release bytes and the original unsigned receipt unchanged; it binds the confirmed draft tag's intended final asset URL and a 365-day validity. GitHub's actual draft browser URL is temporary (`untagged-*`); it must not enter a final receipt. The intended final URL is explicitly pending anonymous publication verification, not claimed public now. The workflow rechecks draft status before retaining only the signed receipt as public candidate metadata. It never uploads a real binary to Actions, publishes a Release, modifies `published/` or changes the formal market. Final approval still applies to exact release/receipt/market bytes, followed by anonymous revalidation.

Renaming `publisherKeyId` in an old signed receipt is invalid signature tampering. After the original private keys proved unavailable, the publisher explicitly authorized independent replacements. Keys were generated in an owner-only temporary directory and transferred as Base64 through anonymous `gh secret set` stdin to the two Environment secrets; temporary seed files and directory were deleted. No private value was printed or committed. GitHub derived-key verification and actual candidate signing succeeded, and Rust Host verified both signed receipts against the original ZIP digests. Old installations/native components were first removed through normal Host operations and maintenance ACKs; inactive test copies and obsolete records/candidates were then cleaned after terminal-state and ownership checks. The Host and importer have no previous-key/alias/grace-period support. Retired signatures are rejected, and new signatures cannot borrow an old acceptance. Further root rotation requires explicit authorization. Signed drafts are not Stable releases; final publication and formal Marketplace changes still require approval.

## Isolated first Stable review

After both existing drafts have their verified `signed-receipt.json` asset, dispatch `sign-market-candidate` on the reviewed `main` commit. Supply the independent RFEM digest as `archive_sha256` and Rhino digest as `rhino_archive_sha256`. Both drafts must still target that exact commit. This T35 review mode requires the formal discovery list to be empty and no formal signed snapshot to exist: it cannot overwrite an existing Stable market.

The same secret boundary validates both primary keys, then reuses the complete archive/MCP verifier, `generate_stable_view.py`, `generate_marketplace.py` and `sign_marketplace.py`. Release-package scope is checked before deriving the generated market authorization; market-signing scope cannot authorize another publisher's release. First sequence is 1. Work occurs in a fresh temporary directory, and only the portable review is atomically retained. No runtime ZIP, extracted Provider, private key, local source path or business data enters that artifact. The public review contains `published/<id>/`, `.agents/plugins/marketplace.json`, `.agents/plugins/marketplace.snapshot.json`, and a digest/view inventory in `review.json`. Its name, report and pending URL checks identify it as an unapproved candidate, not a formal source.

Download and verify these exact review bytes against the Host roots before requesting final approval. Native execution still requires the signed Windows ZIP and compatible Host; another Agent Plugins client must not infer general native executability from a portable view. Existing generic release/view/signing tools retain independent plugin version inputs; this first-publication review mode is not an automatic updater or publication service. The formal `published/` and Marketplace files remain unchanged until the publisher approves the concrete candidate and the released assets pass anonymous verification.

## Generate from immutable verified inputs

Every artifact build requires an explicit publisher `--release-sequence`; there is no default counter. It is independent of the marketplace snapshot sequence. Advance the package/variant counter and root version for changed assets; never reuse a published version, reset Host trust history or rebind an old counter to new ZIP bytes. Root Manifest remains the sole human-maintained plugin identity.

Generate inputs with `python -B scripts/build_artifact.py plugins/<id> --generate-release-input --release-sequence <counter>`. One invocation derives the root `packaging/release-input.json` from root bytes and publisher counter, and synchronizes an existing Provider copy used by its build. It does not create unused Provider input files. Build with the same explicit counter and a fresh external output directory; drift is rejected before Provider staging. RFEM embeds and hashes its generated Provider input. Archive verification checks that embedded input against root bytes, release identity and the receipt-bound counter. The synthetic CI fixture explicitly uses counter 1; this grants no signing or Stable approval.

The three Python interfaces are:

```python
generate_stable_view(artifact_root, receipt, output_root,
                     trust_policy=policy, verified_context=verification)
generate_marketplace(bindings, output, view_root=output_root,
                     trust_policy=policy, artifact_roots=roots,
                     verified_contexts=verifications)
sign_marketplace(raw, bindings, sequence, signer, views=views,
                 trust_policy=policy, view_root=output_root,
                 artifact_roots=roots, verified_contexts=verifications)
```

Nonempty inputs fail closed without caller-controlled authorization and immutable extracted artifact roots. The policy is release-tool input, not a plugin manifest, second identity catalog or Host runtime contract. It contains the exact `repositoryIdentity`; `keys` indexed by key ID, with raw public-key hex, authorized package IDs, validity times and explicit `revoked=false`; `approvedArchives` mapping approved archive digests to actually confirmed URLs; `revokedArchives`; and, for marketplace signing, `marketplaceKeyId` and the previously accepted `previousSequence`. Authorization and confirmed URLs come from the publisher, never from the receipt's self-assertion. No production trust or approval is included in this repository. Test policies and ephemeral signers authorize only synthetic test inputs inside temporary folders.

T07 independently verifies the signed Windows archive with `scripts/verify_artifact.py`, returning `archiveDigest`, `filesDigest`, `toolCatalogDigest` and `verification="signed-receipt"`. Provide that result as `verified_context`. It is a cross-check/cache record, not cryptographic proof: generation still independently verifies the receipt signature, authorized repository/package/key/time/revocation, release bytes, full closed inventory, every file digest, root identity and preview/SBOM bindings. It never executes Provider/MCP just to project a static view. Marketplace generation and signing repeat those checks and compare every active view file to the approved artifact projection. No current development root is scanned for formal discovery.

Authenticated `revoked=true` receipts are revocation-only bindings. They require a current authorized signer, exact source/package scope, valid signature and validity window, and explicit previously approved archive URL/digest history in the caller's `approvedArchives`. They remain in snapshot `releases` but never create a discovery entry, active view or runtime permission; no artifact root/context is needed for a tombstone. An old revoked archive and a distinct new active archive can share a package ID, producing one active view. Duplicate or conflicting statements for an exact archive and multiple active releases of one package are rejected. Active receipts for locally known revoked archives remain rejected. This producer support is available now for the later Host consumer; it does not publish a formal Stable snapshot or implement Host persisted revocation.

The shared official JSON-schema validator installs `FormatChecker` guards for exported signed/unsigned integer-width formats rather than copied field schemas; receipt/snapshot numeric widths therefore match the authoritative owner. Caller-policy times are explicitly bounded to uint64. Both archive extraction and static projection use the same `MAX_ARCHIVE` and `MAX_FILE` limits. Static projection validates every file's stat size and aggregate size before reading any content, then reads bounded bytes and rejects size changes.

CLI examples below describe input files supplied by the controlled publisher; no approved input files or asset URLs exist yet. Keep these inputs and outputs in ignored `dist/` or an external candidate directory. `artifact-roots.json` is a temporary map of package IDs to verified extracted artifact directories; `verified-contexts.json` maps the same IDs to verifier results. `views.json` contains the owner-exported `StableViewInventoryV1` records, generated with `inventory_for` from the verified portable bytes.

```powershell
python -B scripts/generate_marketplace.py --view-root . --output dist/candidate/marketplace.json
# In the existing independent fixture/Provider tooling environment:
python -B scripts/generate_stable_view.py <verified-artifact-root> <signed-receipt.json> --policy <publisher-policy.json> --verified-context <verification.json> --output-root dist/candidate
python -B scripts/generate_marketplace.py --bindings <approved-bindings.json> --view-root dist/candidate --output dist/candidate/marketplace.json --policy <publisher-policy.json> --artifact-roots <artifact-roots.json> --verified-contexts <verified-contexts.json>
python -B scripts/sign_marketplace.py --marketplace dist/candidate/marketplace.json --bindings <approved-bindings.json> --views <views.json> --policy <publisher-policy.json> --artifact-roots <artifact-roots.json> --verified-contexts <verified-contexts.json> --view-root dist/candidate --sequence <next-sequence> --output dist/candidate/marketplace.snapshot.json
```

The standalone signing command receives exactly 32 raw private-key bytes on anonymous stdin, after validating public inputs. Never put private keys in arguments, persisted environment configuration, logs or plugin runtime dependencies. The controlled Actions entrypoint's transient step-scoped injection is described above. Only public keys occur in policy input. The signer must match the authorized marketplace key; sequence must increase; the snapshot validity is bounded by every receipt and signer authorization. Signing uses T07's canonical Ed25519 helper and the exported `SignedMarketplaceV1`/`StableViewInventoryV1` owner schema, not duplicated schema declarations. A required engineering API key gates connection, not package installation.

Views retain original root, complete Skills/resources, assets and same-origin configuration/preview/README bytes. Broken relative Markdown references, undeclared files, reparse points and missing resources reject generation. Managed native entrypoints and Yak/runtime files resolve only in the signed Windows install asset; they cannot resolve in the portable view. The first managed plugins have no standard `mcp.json` and no fake executable endpoint is generated. Root versions come from the verified manifest; the official discovery entry has no manually copied version and uses `./published/<id>` relative to the repository root. Current engineering categories are `Engineering Design`, not a global category taxonomy.

## Final publication and failure preservation

For a subsequent market, `operation=sign-market-update` takes the selected plugin, its reviewed `archive_sha256`, and `previous_market_sha256` for the exact current signed snapshot. It downloads each unchanged published plugin or skill archive and retains its exact signed receipt. The signer verifies the prior market signature, per-package signatures and publisher scopes, discovery bytes and complete published inventories before preparing sequence `previous + 1`. An unchanged package may be retained only with its exact previously signed receipt and verified published archive; a changed package must advance both version and release sequence. The initial `sign-market-candidate` operation still refuses an existing market. Revocation/tombstone changes are outside this update operation. Signing retains isolated public review metadata; the controller verifies publication and submits the complete market/view tree atomically.

`release-skill.yml` adds a bounded, manual pure-skill path. `sign-skill-draft` checks the exact source-commit draft and reviewed archive digest before signing its receipt. `sign-skill-market` additionally pins the prior signed market digest, downloads and independently verifies the previously published archives, retains their exact signed receipts, and produces a signed review containing the new skill and previous packages. The workflow uses the existing protected `plugin-signing` Environment, uploads only public receipt/review metadata, and does not publish releases or edit formal discovery. The controller performs the final release, anonymous asset verification and atomic market publication described below.

Daily development retains source changes in Git, not copies of version directories. Tests/builds use system temporary directories; do not create logs, reports or temporary build directories beside the repositories. Only explicit release preparation produces versioned archives. Temporary candidate ZIPs, extracted runtimes, signatures and logs are removed after upload/publication checks; Git tags and immutable GitHub Releases retain formal versions. Routine tasks do not leave local validation reports or candidates as deliverables.

1. Independently build each plugin from its root version and frozen lock; complete required real software/native acceptance separately. RFEM/Rhino tags are independent: `plugin-<id>-v<root-version>`.
2. With explicit candidate-operation authorization, prepare actual draft Releases and verify authenticated downloads. A GitHub draft requires a tag name and is not anonymous public-download proof. The signing workflow reads an already prepared exact-commit draft; it does not create one or publish it.
3. Sign receipts under confirmed authorization, verify exact draft asset bytes, and generate candidate view, official discovery and signed snapshot in ignored output. Review exact bytes, digests, signer scope, validity, known revocations and candidate report.
4. Obtain final publisher approval for those exact inputs. Publish the immutable Stable release, anonymously download and reverify its actual URL and bytes. No invented or unconfirmed release URL may enter approved inputs.
5. Only after successful anonymous revalidation, publish the approved views, official discovery file and signed snapshot together in one `main` Git tree. Preserve `/published/** -text` and marketplace byte attributes so checkout does not change signed bytes. Consumers read this single commit consistently.

Failed validation leaves previous marketplace bytes untouched; an existing Stable projection can only be reused byte-identically and is never overwritten by a changed candidate. A new development version does not update discovery or the approved view. Failed publication/download/signing must retain the prior trusted market/view; never overwrite immutable tags/assets or repair Git byte drift by resigning altered files. Host cache, installation trust, rotation and persisted revocation remain Host responsibilities in later tasks.

Syntax parsing/local commands are not evidence of a GitHub Actions run. The controller must push the verified change, dispatch `verify.yml`, and confirm the actual run's exact `headSha` and all applicable successful jobs. `notPresent`, queued or skipped work is not proof that a real Provider passed.
